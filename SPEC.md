# SPEC — RpgCore

Плагин для Youer 1.21.1 (гибрид Bukkit + NeoForge, ядро на базе Mohist),
который поэтапно заменяет связку MMOCore + MMOItems + MythicLib + MythicMobs.
Клиентский мод — пятый этап, только презентация.

Статус: **черновик на утверждение.** Код не начинается до приёмки.

---

## 1. Зачем это делается

Текущая связка работает, но стоит дорого в сопровождении по трём причинам,
и каждая из них — требование к новому плагину, а не пожелание.

**Один скилл размазан по четырём файлам в четырёх плагинах.** Механика в
MythicMobs, привязка в MythicLib, числа и лор в MMOCore/skills, выдача классу
в MMOCore/classes. Рвётся любое звено — навык молча не работает, и в логах
ничего нет.

**Механики накладываются друг на друга непредсказуемо.** У каждого плагина свой
конвейер урона и свой набор состояний, и ни один не знает про чужие. Игрок
видит это как «стан не сработал» или «щит не помог».

**Неправильное использование выглядит как правильное.** Механика принимает
конфиг, пишет в лог «Executing» и не делает ничего. Отличить «не то» от
«не работает» по конфигу нельзя.

Цель не «сделать свой MythicMobs», а убрать именно эти три свойства.

---

## 2. Решения, принятые до старта

| Решение | Выбор | Почему |
|---|---|---|
| Объём | Полная замена связки, поэтапно | Решено владельцем |
| Скиллы | Свой мини-DSL, новые примитивы дописываются в код | Решено владельцем |
| Числа | Вынесены из логики в слой баланса | Решено владельцем |
| Контент | Пока 24 навыка мага и плута, конвертер позже | Решено владельцем |
| Клиент | Плагин + мод, мод необязателен | Решено владельцем |
| Сборка | Gradle 8.10.2 через враппер | Дистрибутив уже в кеше профиля |
| API | `io.papermc.paper:paper-api:1.21.1-R0.1-SNAPSHOT`, `compileOnly` | Выкачан, лежит в кеше, собирается офлайн |
| JDK | 21 | Стоит на машине, требуется ядром |
| Рантайм-зависимости | **Нет совсем** | См. ниже |
| Хранение данных | Плоские файлы JSON, один на игрока | См. ниже |

**Почему нет рантайм-зависимостей.** Их пришлось бы либо шейдить, либо тянуть
через library loader Paper, то есть качать с сервера при запуске. SnakeYAML уже
есть в classpath ядра (на нём работает `YamlConfiguration`), и его node-API даёт
номера строк — это всё, что нужно M5. Никаких других библиотек этап 1 не
требует. Решение пересматривается, только если появится задача, которую нельзя
закрыть тем, что уже в ядре.

**Почему плоские файлы, а не SQLite.** Драйвер SQLite — это рантайм-зависимость
со всеми последствиями выше, а игроков сейчас 44. Один JSON на игрока читается
при входе, пишется асинхронно при выходе и по таймеру. Триггер пересмотра
записан явно: больше 500 игроков в базе или заметные задержки на записи.

## 3. Команды

```
./gradlew build                 сборка и тесты
./gradlew test                  только тесты
./gradlew :plugin:jar           собрать плагин
./gradlew build --offline       сборка без сети (после первой выкачки работает)
```

В игре:

```
/rpg validate                   проверить весь контент, ничего не применяя
/rpg reload <домен>             перегрузить контент домена
/rpg debug <игрок>              показать снимок статов и активные статусы
/rpg why <игрок> <статус>       почему статус не наложился или подавлен
/rpg cast <навык>               применить навык со всеми проверками
/rpg cast <навык> raw [ур]      запустить навык в обход маны и перезарядки
/rpg slot <номер>               применить навык из слота
/rpg mana                       запас маны, перезарядки, запрещающий статус
/rpg class <класс>              выбрать класс
/rpg unlock <навык>             изучить навык
/rpg upgrade <навык>            вложить очко в уровень навыка
/rpg bind <слот> <навык>        повесить навык на слот
/rpg skills                     навыки своего класса и их состояние
/rpg                            открыть интерфейс (то же, что /rpg menu)
/rpg items                      список объявленных предметов
/rpg give <предмет> [сколько]   выдать себе предмет (только администратор)
/rpg mobs                       список мобов и правил спавна
/rpg spawn <моб>                поставить моба перед собой (администратор)
/rpg convert                    перенести мобов из convert-in (администратор)
/rpg client                     у кого стоит клиентский мод и версия протокола
/rpg reset <игрок> <что>        обнулить игрока: all, class, skills, slots, progress
/rpg progress                   уровень, опыт, очки, разложенные слоты
/rpg xp <сколько>               выдать себе опыт (только администратор)
```

Права разделены: `rpgcore.play` (всем) — свои класс, навыки и слоты;
`rpgcore.admin` (операторам) — `validate`, `reload`, `debug`, `why`, `xp` и
`cast ... raw`.

`/rpg why` — не отладочная роскошь, а требование: любой отказ в наложении
статуса должен объясняться одной командой. `/rpg mana` — то же требование для
каста: всё, что решает исход нажатия, видно одной командой.

## 4. Структура проекта

Один Gradle-подпроект, модули карты — пакеты внутри него. Отдельные
Gradle-модули на этом размере дали бы только накладные расходы; направление
зависимостей обеспечивается тестом, который сканирует импорты и падает на
запрещённом направлении.

```
C:\ProjectSt\RpgCore
├─ SPEC.md                       этот документ
├─ settings.gradle.kts
├─ build.gradle.kts
├─ gradlew, gradlew.bat, gradle/wrapper/
├─ docs/                         решения по ходу, ADR
└─ plugin/
   └─ src/
      ├─ main/java/ru/projectst/rpgcore/
      │  ├─ RpgCorePlugin.java           точка входа, сборка графа объектов
      │  ├─ loader/                      M5 — строгая загрузка
      │  ├─ stat/                        M1 — реестр статов
      │  ├─ damage/                      M2 — конвейер урона
      │  ├─ status/                      M3 — статусы и конфликты
      │  ├─ data/                        M4 — данные игрока
      │  ├─ skill/                       M6 — DSL (этап 2)
      │  ├─ balance/                     M7 — числа (этап 2)
      │  ├─ classes/                     M8 (этап 2)
      │  ├─ cast/                        M8 — ворота каста (этап 2)
      │  ├─ gui/                         M9 (этап 2)
      │  ├─ item/                        M10 — предметы (этап 3)
      │  ├─ craft/                       M11 — рецепты (этап 3)
      │  ├─ mob/                         M12 — мобы (этап 4)
      │  ├─ convert/                     M13 — конвертер (этап 4)
      │  └─ platform/                    всё, что трогает Bukkit напрямую
      ├─ main/resources/                 paper-plugin.yml, схемы, дефолтный контент
      └─ test/java/                      юнит-тесты
```

**Правило `platform/`.** Классы Bukkit импортируются только в `platform/` и в
точке входа. Остальные пакеты работают через интерфейсы, которые `platform/`
реализует. Это не академическая чистота: именно это делает M1–M3 проверяемыми
юнит-тестами без запуска сервера.

Направление зависимостей: `loader` и `stat` не зависят ни от кого;
`damage` → `stat`; `status` → `stat`, `damage`; `data` → `stat`; `cast` →
`classes`, `skill`, `balance`, `status`, `stat`; всё остальное смотрит на них.
Обратных стрелок нет.

## 5. Этап 1 — спецификация модулей

### M5 · loader — строгая загрузка контента

Закрывает требование «никаких тихих отказов».

Загрузка в две фазы. **Разбор:** YAML читается node-API SnakeYAML, поэтому у
каждого ключа известны файл, строка и колонка. Схема домена описывает
обязательные и допустимые ключи, типы и диапазоны. **Связывание:** проверяются
перекрёстные ссылки — скилл на класс, скилл на статус, предмет на стат,
конфликт на существующий статус.

Ошибкой считается: неизвестный ключ, отсутствие обязательного, несовпадение
типа, значение вне диапазона, ссылка в пустоту, дубликат id. Каждая ошибка
несёт `файл:строка:колонка`, имя ключа и что ожидалось.

Отказ **закрытый, но локальный**: битый файл отключает свой элемент контента с
громкой ошибкой в консоль и в `/rpg validate`, но не роняет сервер и не мешает
остальному контенту. Сервер должен оставаться играбельным — это требование
этапа важнее строгости.

`/rpg validate` выполняет обе фазы, ничего не применяя, и выводит сводку:
сколько файлов, сколько элементов, сколько ошибок, список ошибок.

Проверяется юнит-тестами: на вход подаются заведомо битые файлы, проверяется
не только факт ошибки, но и номер строки в тексте.

### M1 · stat — реестр статов

Стат: `id`, отображаемое имя, тип (`FLAT`, `PERCENT`, `MULT`), значение по
умолчанию, минимум, максимум, правило округления.

Источники значений: база класса с кривой по уровню, предметы, статусы,
временные надбавки. Порядок агрегации фиксирован и документирован:

```
база → сумма FLAT → сумма PERCENT → произведение MULT → ограничение min/max
```

Снимок статов на игрока считается один раз и кешируется; при изменении любого
источника кеш сбрасывается **одним** путём инвалидации, а не из десяти мест.

Отдельно описывается отображение на ванильные атрибуты для тех статов, где это
обязательно: `max_health`, `movement_speed`, `knockback_resistance`,
`attack_speed`. Остальные живут только внутри плагина.

Проверяется юнит-тестами целиком: это чистая арифметика.

### M2 · damage — единый конвейер урона

Единственная точка входа:

```
DamageRequest{ source, target, base, school, tags, skillId }  →  DamageResult
```

Порядок обработки:

```
1. база
2. масштабирование от статов атакующего по школе урона
3. бросок крита
4. снижение от статов цели: сопротивления, процентное, плоское
5. щиты — поглощают до нуля, остаток идёт дальше
6. неуязвимость и отмена
7. применение
```

Перед шагом 7 испускается одно событие Bukkit, чтобы региональные плагины
(Lands, Factions) могли отменить урон. Отменённый урон не применяется и
отражается в `DamageResult`.

**Жёсткое правило:** `LivingEntity#damage` вызывается ровно в одном классе
внутри `platform/`. Любой другой путь нанесения урона — ошибка ревью. Это и есть
«один конвейер»; без этого правила требование не выполняется.

Проверяется юнит-тестами на подставных поставщиках статов плюс один
интеграционный тест на отмену события.

### M3 · status — статусы и конфликты

**Главный модуль проекта.** Он небольшой, но именно он закрывает основную боль,
поэтому пишется до первого скилла, а не после.

Статус: `id`, категория, длительность, максимум стаков, теги, приоритет и
объявленные отношения. Категории: `CONTROL`, `BUFF`, `DEBUFF`, `SHIELD`,
`IMMUNITY`, `MARK`.

Отношения объявляются **в конфиге, а не в коде**:

| Отношение | Смысл |
|---|---|
| `suppresses: [ids]` | пока A активен, B не действует, но продолжает тикать |
| `removes: [ids]` | наложение A удаляет B |
| `blocks: [ids]` | пока A активен, B вообще не накладывается |
| `exclusive: <категория>` | одновременно активен только один статус категории |
| `stacking: NONE / REFRESH / EXTEND / STACKS` | поведение при повторном наложении |
| `priority: <int>` | кто кого вытесняет в `exclusive` |

**Наложение всегда возвращает явный исход:** `APPLIED`, `REFRESHED`,
`REPLACED(id)`, `BLOCKED_BY(id)`, `SUPPRESSED_BY(id)`. Молчаливого «ничего не
произошло» не существует. Исход попадает в отладочный лог с именем сработавшего
правила, и его же показывает `/rpg why`.

Граф конфликтов проверяется при загрузке: цикл в `suppresses` — ошибка,
статус, подавляющий сам себя, — ошибка, ссылка на несуществующий id — ошибка.

Связь с M2: статус категории `IMMUNITY` отменяет урон на шаге 6, `SHIELD`
поглощает на шаге 5. Обе точки — внутри единого конвейера, а не отдельными
слушателями.

Проверяется матричным тестом по всем объявленным отношениям.

**Надбавки к статам живут сроком статуса.** Навык привязывает надбавку к
статусу (`modify-stat` с ключом `status`), и она держится ровно столько, сколько
статус на цели: истёк, снят, развеян, вытеснен — надбавка уходит; подавлен — не
действует, но вернётся вместе с ним; не лёг (заблокирован) — не ложится и она.
Своего таймера у такой надбавки нет: два срока у одного эффекта однажды
разошлись бы. Раньше надбавка жила отдельным таймером, и развеянная Пелена
оставляла скорость до конца срока, а показать игроку «Пелена: +12% скорости»
было нечем. Сверка — `StatusStats`, каждый тик для тех, у кого привязки есть.

Источник такой надбавки — `status:<статус>:<стат>`, один на пару, поэтому
повторное наложение заменяет надбавку, а не складывает. Общие дебафы навыков без
своего статуса — `slowed`, `exposed`, `weakened` — тоже общие по этой причине:
два замедления от разных навыков не складываются, действует последнее.

Статус без `display` — служебный (замок, отметка «уже сработало») и игроку не
показывается. `description` — что статус делает, в два-три слова: «без
навыков», «гасит удар»; пишется под значком, когда чисел нет.

### M4 · data — данные игрока

Хранится: класс, уровень, опыт, нераспределённые очки, разблокированные навыки,
привязки слотов. Статусы не сохраняются — они транзиентны по смыслу.

Один JSON на игрока. Чтение при входе в основном потоке, запись асинхронная при
выходе и по таймеру. Схема версионируется, миграции применяются при загрузке.

Команда экспорта в читаемый YAML для разбора проблем и бэкапа.

Проверяется round-trip тестами: запись, чтение, сравнение.

## 6. Этапы 2–5 — контуры

Подробная спецификация каждого модуля пишется перед его этапом, а не сейчас:
формат DSL нельзя заморозить до того, как существует M3, иначе придётся
переписывать.

**Этап 2 — M7 balance, M6 skill, M8 classes, часть M9 gui.** Числа отдельным
слоем, DSL с одним файлом на скилл и явным конвейером целей, затем классы и
слоты. По завершении классовые навыки уходят от MMOCore и MythicLib. Перенос 24
навыков мага и плута — приёмочный критерий этапа.

Сделано: слой баланса, DSL с примитивами и условиями, связывание ссылок,
классы со ступенями и слотами, ворота каста, активация слотов нажатием, опыт и
уровни, зоны, снаряды, призыв, триггеры, **перенос 24 навыков**, интерфейс (M9).
Этап 2 закрыт.

**Перенос состоялся.** Двадцать четыре активных навыка, по шесть на класс: маг
на печатях, друид на двух счётчиках, колдун на душах, плут на силе духа. Один
файл на навык, числа ссылками в баланс, служебные навыки класса рядом с теми, к
которым относятся.

Приёмка — не список в коде, а тест, который читает каталоги `skills/` и
`classes/` с диска и связывает всё найденное. Поэтому новый навык попадает под
проверку самим фактом существования: забытая строка в списке была бы такой же
тихой дырой, от которой уходит весь проект.

Что добавилось в DSL по ходу переноса — добавилось потому, что иначе навык не
выражался, а не «на будущее»:

| Примитив | Чей навык его потребовал |
|---|---|
| `origin: self \| forward N` у шага | Сгон и Коллапс мага: точка сбора впереди, а не под ногами |
| цель `enemies_near_zone` | Коллапс: тянет тех, кого накрыли печати |
| `limit` у цели | Метка жатвы, Удар из тени: ближайший, а не кто попало |
| `min-gap` у зоны | печати мага: касты на месте не копят их в одну точку |
| `on-enter`, `on-tick` у зоны | Цвет бездны, Тёмная пелена, Отражение |
| служебные навыки (`internal`) | ядро печатей, ответ коры, счёт ударов метки |
| `dash`, `approach` | Рывок и Удар из тени плута |
| `restore` | Веер клинков: ресурс класса за каждое попадание |
| `count` (цели и стаки) | Переливание душ, Кокон, Метка смерти |
| `remove-status` со `stacks` | заряды коры друида |
| `clear-potion` | Шаг призрака: невидимость рвётся ударом |
| `yaw-offset` у снаряда | Россыпь: веер из пяти печатей |
| задержка шага ссылкой в баланс | жатва колдуна: срок проклятия задан числом |
| `status` у `modify-stat` | бафы и дебафы на экране: число должно знать, чей оно эффект |

Надбавка со `status` берёт срок у статуса, поэтому `duration` при ней — ошибка
загрузки. Связывание проверяет, что статус кладёт этот навык (в любом шаге) или
навык, который его вызывает, и что в том же шаге статус стоит раньше надбавки:
иначе в момент надбавки статуса ещё нет, и она не ляжет никогда. Шире «тот же
шаг» правило потому, что так устроен контент: Жар берсерка кладётся первым
шагом, а надбавка — вторым; прибавку Глухой Обороны считает отдельный навык,
которого вызывает тот, кто кладёт статус.

**M9 · интерфейс.** Ванильные окна инвентаря, без клиентского мода: экран
персонажа, выбор класса, навыки, слоты и статы.

Три решения, которые стоит держать в голове при правках.

Щелчок разбирает сам экран, через владельца инвентаря. Обычный способ —
сравнить заголовок окна и угадать по номеру ячейки — ломается от правки текста
и начинает молча пропускать щелчки дальше, в инвентарь игрока. Любое действие в
окне отменяется до разбора, иначе иконку можно вытащить себе, и кнопка станет
бесплатным предметом.

Экран собирается заново при каждом открытии и после каждого действия. Экран,
показывающий прежние числа после нажатия, — такая же тихая ложь, как стат,
которого нет в мире.

Под каждым навыком написано, что мешает: уровень, очки или достигнутый максимум.
Кнопка, которая просто не реагирует, — это то самое нажатие впустую без причины,
и в интерфейсе оно хуже, чем в бою: игрок видит навык и не понимает, почему он
недоступен. Числа стоимости и перезарядки берутся из той же таблицы баланса,
которой пользуется бой, а статы — из того же снимка, что берёт конвейер урона:
отдельный расчёт для показа означал бы два источника правды.

**Окно снаряжения (закладка «Снаряжение» в книге героя мода).** Тринадцать
ячеек: шлем, нагрудник, поножи, сапоги, вторая рука, два кольца, амулет,
браслет, перчатки и три артефакта, а под ними — сумка игрока. Предмет в ячейке
своего слота (`slot: ring`, `amulet`, `bracelet`, `gloves`, `artifact`, броня —
своим слотом, `any` — в любой) считается надетым: его надбавки идут тем же
механизмом, что надбавки шлема, — свой источник на ячейку, те же требования, те
же отказы словами. Снятый предмет перестаёт считаться сам, без команды «убрать».

Ячейки двух родов. Броня и вторая рука — **ванильные**: окно показывает и
меняет настоящую экипировку, поэтому надетое видно на модели, совпадает с
обычным инвентарём и падает со смертью, как всегда. Кольца, амулет, браслет,
перчатки и артефакты в ванильной броне не живут и лежат **в данных игрока**:
не выпадают со смертью, не теряются при полной сумке. Записаны целиком, со
всем, что на них есть, — хранить один идентификатор было бы короче, но тогда
снятое возвращалось бы не тем, что надели. Слой данных при этом про предметы
Bukkit не знает: он хранит строку по имени ячейки, а что внутри, знает только
платформа.

**Вещи таскаются курсором, а переносит их сервер.** Окно — настоящий контейнер
на два ряда: только у контейнера бывает курсор с вещью, и только так работает
перетаскивание. Но ячейки контейнера — витрина: каждый щелчок по ним
отменяется, и сервер сам читает настоящее содержимое ячейки, проверяет вещь на
курсоре, кладёт, забирает или меняет местами, а потом перерисовывает витрину.
Ванилле здесь доверить нечего — она не знает, что кольцо не шлем, и записала бы
в витрину то, чего нет нигде. Поэтому у вещи в каждый момент ровно одно место:
курсор, сумка или ячейка, — а закрытие окна ничего не копирует обратно.
Shift-щелчок по вещи в сумке надевает её в первую подходящую свободную ячейку
(кольцо — сначала на левую руку), по ячейке — снимает ровно столько, сколько
влезло в сумку.

Мод узнаёт контейнер по ключу заголовка `rpgcore.gear.title` и рисует его своим
экраном: те же номера ячеек, но на местах раскладки, с куклой игрока и
силуэтами пустых ячеек. Ванильные координаты ячеек неизменяемы, поэтому мод не
переставляет ячейки сундука, а подменяет меню своим с тем же номером окна и тем
же порядком — без миксинов и правки чужих классов. Порядок ячеек — договор
сторон (`Protocol.GEAR_CELLS`), и его расхождение с плагином ловит тест.
Ячейка, в которой вещь лежит, но не действует, обведена красным, причина — в
подсказке; отказы сервера на щелчки показываются в самом окне.

Без мода окна снаряжения нет — это решение владельца: старое сундучное окно
артефактов и команда `/rpg artifacts` убраны. Ни один вид `/rpg reset`
снаряжение не трогает: в ячейках лежат вещи игрока, а не его прогресс.

Ячеек артефактов стало ровно три, настройка `artifact-slots` убрана. Артефакты
из прежних слотов 1–3 переехали в новые ячейки при чтении данных (схема 4);
лежавшие дальше ушли в очередь возврата и отдаются владельцу при входе — в
инвентарь, а что не влезло, под ноги. Молча пропасть вещь не может.

**Верстак предметов (`/rpg forge`).** Админское окно: собрать предмет со статами
прямо в игре и получить его в руки. Нужен проверке навыков — навык читает статы
носителя, и «как влияет плюс сорок к магическому урону» проверяется только
надетым предметом, который его даёт.

Собранный предмет становится **файлом контента**, а не временным предметом. Статы
снаряжения читаются по объявлению, найденному в реестре по метке в самом
предмете; предмет, живущий только в памяти верстака, потребовал бы второго пути к
статам, а второй путь однажды расходится с первым — и выглядит это как «предмет
надет, а цифры не изменились».

На диск попадает только то, что читается. Порядок жёсткий: черновик проверяется
сам, превращается в объявление, печатается в текст, **читается обратно своим же
загрузчиком** и связывается с контентом. Любая осечка — отказ со строками
загрузчика, и файла не создаётся: опечатка в верстаке иначе отключила бы домен
предметов при следующей загрузке, причём у всех. Писатель формата и загрузчик
живут в двух методах и могут разъехаться — плата по этому счёту
`ItemDefWriterTest`: объявление → файл → объявление, и сверка с исходным.

Статы выбираются из загруженного `stats.yml`, выдумать их в верстаке нельзя. Плюс
отдельная сверка с живым движком статов: реестр он получает при запуске, и стат,
дописанный в файл на ходу, прошёл бы связывание, но не применился бы — молча.
Верстак на такое отказывает и говорит, что нужен перезапуск.

Это же вскрыло общий предел `/rpg reload`: службы получают реестры при запуске и
подменой реестра в `ContentService` не пересобираются. Предметы теперь спрашивают
реестр каждый раз (`RpgItems`), рецепты перерегистрируются. Навыки, классы, мобы и
баланс после reload остаются прежними до перезапуска — и это стоит исправить
отдельно, а не делать вид, что reload применяет всё.

Иконки лежат в контенте (`icon:` у навыка и у класса), а не в таблице внутри
кода: иначе добавить навык было бы нельзя без правки Java. Неизвестный материал
подменяется бумагой — опечатка в иконке не должна мешать пользоваться навыком.

**Ресурс объявляет класс.** Маг платит маной, воин силой духа — один механизм
с разными статами, а не два пути проверки, как было, когда ману считал MMOCore,
а выносливость MythicLib. В файле навыка это ключ `cost:`, а не `mana:`: ключ,
названный по одному классу из одиннадцати, читался бы как ложь в остальных
файлах.

**Выносливость — второй запас, и он общий.** Есть у каждого игрока независимо от
класса, и ресурсом класса быть не может: из неё платится врождённый рывок, и
будь она одна с ресурсом класса, уклонение покупалось бы уроном — «нечем
отступить» означало бы «нечем ударить». Попытку объявить её ресурсом класса
загрузчик называет ошибкой.

**Врождённый рывок.** Один навык (`innate: true`) есть у всех с первого уровня:
его не изучают, он не занимает слот и не принадлежит классу — отступить должен
уметь и тот, кто класс ещё не выбрал. Три заряда, каждый возвращается сам,
считая от своей траты. Идёт он туда, куда игрок **бежит**, а не куда смотрит:
клиент присылает нажатые клавиши движения, а направление по ним считает сервер
по повороту, который видит сам. Поэтому подменённый мод может попросить одну из
восьми сторон, а не любую точку мира.

Врождённый навык ровно один, и это проверяет связывание: у клавиши рывка нет
второго адресата, а «какой-нибудь из двух» было бы решением, принятым порядком
файлов в папке.

**Обездвиженный не перемещается.** Навык, двигающий кастера — рывок, телепорт,
сближение, — под статусом с меткой `immobilize` отказывает. Проверка одна на все
такие навыки и стоит в воротах каста: будь она в самих навыках, забытый навык
означал бы бесплатное снятие корней.

**Статы — рейтинги, а не проценты.** Значение стата растёт числом и ничем не
ограничено сверху, а сколько процентов оно даёт, считает кривая насыщения,
объявленная в самом стате:

```
процент = cap * рейтинг / (рейтинг + cap)
```

У кривой один параметр — предел, к которому она стремится и которого не
достигает ни при каком значении. Поэтому потолка сверху больше нет нигде: ста
процентов уклонения, снижения перезарядки или защиты не бывает в принципе, и
очередной пункт стата не может молча перестать что-либо значить — а именно так
вели себя старые ограничения вида «не больше восьмидесяти процентов».

Наклон у нуля единичный: первые пункты рейтинга дают примерно столько же
процентов, сколько их самих. Это сохранило смысл числам контента, писавшимся
когда-то прямо в процентах, — расходится только верх, где и должна работать
убывающая отдача.

Считается кривая в одном месте (`StatRegistry.share`), и спрашивают её все: шаги
усиления и снижения в конвейере урона, бросок крита, бросок уклонения,
перезарядка в воротах каста, вампиризм, скорости в `VitalsSync`, радиус, сила и
длительность эффектов в исполнителе. Деление на сто по месту означало бы, что
кривая применяется где-то, а где-то нет, и расхождение нашлось бы не тестом.

**Что видит игрок.** Наведя курсор на стат в книге героя или в окне статов, он
читает фразу из файла этого стата: «−60% получаемого физического урона», «+25%
ударов уходит в пустоту». Фраза лежит в контенте рядом с кривой, потому что это
слова для игрока; число в неё подставляет сервер, спросив тот же реестр, которым
считает бой. Запасы — здоровье, мана, сила духа, выносливость и восстановление —
кривой не объявляют вовсе: сто процентов маны не величина, а бессмыслица, и
подсказка о них молчит.

В описании самого предмета процент не пишется намеренно. Вклад одного предмета
зависит от того, сколько рейтинга уже есть: «+12 физического урона» даёт разные
проценты голому и одетому, и написать на кольце одно число значило бы соврать
одному из них. Поэтому на предмете — рейтинг, а проценты — в меню, где виден
итог.

**Щиты складываются.** Два щита подряд — это два щита; замена означала бы, что
второй каст иногда ослабляет защиту, и объяснить это игроку нечем.

**Расхождения с прежними версиями** написаны в самих файлах навыков, рядом с
местом, где они видны: кора друида поглощает удар щитом вместо полной отмены
(зарядов неуязвимости в конвейере урона пока нет), оковы колдуна тянут всех
закованных, а не только далёких (цели выбираются радиусом, а не кольцом),
двойник плута — подставка, а не копия игрока, шанс оглушения у Удара из тени
задан числом, пока нет статов шанса и сопротивления.

**Снаряд.** `projectile` летит, его видно и от него можно отойти; `ray` попадает
мгновенно. Два разных примитива с разными именами, потому что в старом стеке они
настраивались почти одинаковыми ключами и перепутать их было проще, чем заметить
разницу. Шаг полёта режется на отрезки не длиннее половины блока: иначе быстрый
снаряд за тик перескакивал бы цель, и это лечили бы увеличением радиуса
попадания, то есть делали хуже. Снаряд не является сущностью Minecraft — своя
сущность означала бы хитбокс и попадание в выборку целей других навыков, то
есть взаимные помехи между снарядами и зонами.

`on-hit` и `on-end` — два ключа, а не флаг: попадание и промах разные события.
Когда поведение одно («разорваться здесь»), в оба ключа ставится один навык, и
это видно в файле.

**Призыв.** Владелец записывается при постановке на учёт, а не штампуется
обработчиком спавна. Из-за обратного зверь друида оставался бесхозным: заявка на
владение уходила раньше, чем моб появлялся, и до штампа любой волк был своим для
любого друида. Правило «свой призванный не попадает под свои площадные навыки»
живёт в одном месте — в выборке целей, а не в каждом навыке с радиусом. Свой
зверь не бьёт владельца и не берёт его в цель: без второго он бесконечно махал
бы лапами, пытаясь ударить хозяина.

**Триггеры.** Что запускает навык, написано в самом навыке: `on: damaged |
deal-damage | kill | interval`. Пассивка идёт через те же ворота каста, что и
нажатие: стоит маны, уходит в перезарядку, не работает под тишиной. Отдельный
путь означал бы второй набор правил. Повторный вход запрещён по игроку: навык
«когда я наношу урон», сам наносящий урон, иначе звал бы себя до переполнения
стека, и цепочка из двух навыков замкнулась бы так же. Периодический навык
держит свой промежуток через перезарядку, поэтому частота не зависит от того,
как часто его зовёт слушатель. Пассивку нельзя повесить на слот и нельзя
применить вручную — и то и другое названо отдельной причиной, потому что занятый
слот с ничего не делающей кнопкой — это ровно то самое «неправильное
использование, неотличимое от правильного».

Полный список того, от чего навык может сработать, — это список методов
`platform/TriggerListener`. В старом стеке такие строки были рассыпаны по
десяткам файлов, и полного списка не знал никто.

**Раскладка без мода.** Ванильный клиент своих клавиш не присылает, поэтому
берутся те нажатия, о которых сервер узнаёт: Shift + 1…9 применяет навык из
слота, Shift + F показывает ману и перезарядки. Без Shift всё работает как в
ваниле — сменить оружие в бою важнее любой удобной раскладки. Схема живёт в
одном классе `platform/SkillInputListener` и будет заменена клавишами
клиентского мода (M14).

**Зоны (печати).** Своя сущность в `skill/Zone`, а не невидимый моб с
метаданными. В старом стеке зону приходилось изображать армор-стендом, и такой
«моб» отбрасывался выборкой целей на двух стадиях — сначала на поиске
(`livingonly` по умолчанию), потом фильтром, — поэтому печати то работали, то
нет. Здесь зона не является целью ничего, пока её не спросили по тегу; истёкшие
отбрасываются при каждом чтении, а не по таймеру, чтобы ответ «стою ли я в
печати» не зависел от расписания.

Снятие и подсчёт зон — одно действие (`consume-zones`), потому что раздельно
они расходятся: можно посчитать одни печати, а снять другие. Именно это и
случилось со старым Коллапсом, который всегда наносил одинаковый урон.

**Счётчики каста.** Число снятых печатей попадает в счётчик, на который можно
умножить урон: `amount: $damage_per_seal * @seals`. Это весь язык выражений, и
больше его не будет — одно умножение покрывает «за каждую печать», а формулы в
конфиге означали бы отладку арифметики без отладчика. Отсутствующий счётчик
даёт ноль, а не единицу: ноль виден в числе урона, а «как будто одна печать»
искали бы по логам. Счётчик, который никто не заполняет, ловится связыванием.

**Прогресс.** Кривая опыта, предел уровня и очки за уровень объявлены в файле
класса тем же `BalanceValue`, что и всё остальное. Опыт считается от уровня, а
не от общего накопленного, поэтому правка чисел не сдвигает уже достигнутые
уровни. Одно начисление поднимает сразу на столько уровней, на сколько его
хватило: иначе излишек терялся бы молча. На пределе уровня опыт не копится —
копить «в запас» значило бы, что поднятый позже предел выдаёт пачку уровней
сразу, и отличить это от ошибки было бы нечем. Источник опыта пока ванильный
(опыт с убитого моба) и помечен как временный: свои награды мобы объявят в M12.

**Ворота каста (`cast/`).** Единственный вход в применение навыка, и порядок
проверок в нём зафиксирован тестами: право на навык → запрещающие статусы →
перезарядка → запасы. Запасы списываются последними, то есть отказ по любой
другой причине их не трогает. Запасов двое — ресурс класса и выносливость, — и
проверяются оба до списания любого: навык, которому хватило маны и не хватило
выносливости, не должен забрать ману ни за что. Каждый отказ назван отдельной причиной с числами —
нажатие впустую без объяснения было главной жалобой на старый стек, где ману
считал MMOCore, кулдаун — MythicLib, а порядок между ними не был записан нигде.

Запрет каста объявляется контентом, а не кодом: статус с меткой `blocks-cast`
запрещает касты, пока действует. Поэтому новый контроль не окажется молча
кастуемым — метка либо есть в `statuses.yml`, либо её нет.

Мана — стат (`max_mana`, `mana_regen`), а не отдельное число класса: иначе
класс, предмет и навык получили бы три разных способа на неё влиять. Уровень
навыка — вложенные в него очки, и именно он разворачивает кривые баланса,
поэтому вложенное очко видно в уроне, а не только в описании.

**Этап 3 — M10 items, M11 crafting.** Предметы, оружие, инструменты, рецепты.
MMOItems отключается.

### M10 · item — предметы

**Предмет — это объявление, а не предмет в сундуке.** В файле лежит, чем он
выглядит, что даёт, кому разрешён и что умеет; в мире живёт обычный ванильный
предмет с нашей меткой. Метка — запись в постоянном контейнере предмета
(`PersistentDataContainer`), а не строка в описании: описание игрок меняет
наковальней, переводом или другим плагином, и предмет, узнаваемый по описанию,
однажды перестаёт узнаваться. По метке он узнаётся всегда.

**Статы предмета идут тем же путём, что статы класса.** Надетый предмет — это
источник надбавок в `StatService` с именем вида `item:hand`. Поэтому «плюс
двадцать процентов магического урона» от посоха и от класса считаются одним
движком в одном порядке. Отдельного расчёта для предметов нет, и это главное,
что отличает перенос от прежнего стека, где MMOItems считал своё, а MythicLib
своё.

**Требования отказывают названно.** Предмет с требованием по классу или уровню,
надетый не тем, кто может, не даёт статов и говорит, почему: «нужен уровень 12»,
«только для мага». Молча не давать надбавки — худший вариант: предмет надет,
цифры не изменились, и причину не найти.

**Умения предмета проходят через те же ворота каста.** Правый щелчок посохом —
это `CastService`, с маной, перезарядкой и запретом под тишиной. Навык умения
объявлен служебным (`internal: true`) и класса не имеет: его запускает предмет,
а не триггер класса. Связывание проверяет и то, что навык существует, и то, что
он служебный, — иначе умение предмета давало бы игроку доступ к классовому
навыку в обход изучения.

**Редкость объявлена отдельно** (`rarities.yml`): имя и цвет в одном месте.
Цветовые коды, повторённые в каждом предмете, разъезжаются первыми.

**Чего в M10 намеренно нет.** Гнёзда под камни, шаблоны улучшения, элементы и
наборы предметов не переносятся: ни одна из этих механик не нужна, чтобы
отключить MMOItems, а каждая тянет за собой свою экономику. Решение записано
здесь, чтобы при желании вернуть его обсуждали как решение, а не как забытое.

### M11 · craft — рецепты

**Рецепты регистрируются в ванильном верстаке.** Своя станция была бы ещё одним
окном, которое нужно объяснять игроку; ванильный верстак он уже знает.
Ингредиентом может быть материал или наш предмет по идентификатору — во втором
случае сравнение идёт по точному предмету, то есть по той же метке.

**Один файл — один рецепт, и результат ссылается на предмет по идентификатору.**
Ссылка в пустоту ловится связыванием: рецепт, который делает несуществующий
предмет, не должен молча исчезать из верстака.

**Этап 4 — M12 mobs, M13 converter.** Мобы, ИИ, спавн, дроп; конвертер старых
YAML под уже замороженный формат. MythicMobs отключается. Здесь же решается
судьба MythicDungeons и MythicHUD.

### M12 · mob — мобы

**Моб — это объявление, как предмет и навык.** В файле лежит ванильный тип,
здоровье, урон, статы, навыки по триггерам и дроп. В мире живёт обычное
существо с нашей меткой в постоянном контейнере: по ней моб узнаётся после
перезапуска, в отличие от имени, которое меняет первый же бафф или перевод.

**Статы моба идут через тот же движок, что статы игрока.** При появлении моб
получает источник надбавок в `StatService`, и дальше конвейер урона считает его
защиту и урон теми же правилами. Поэтому «магическое сопротивление» у моба
значит ровно то же, что у игрока, — в прежнем стеке у мобов была своя арифметика,
и сравнить два числа было нельзя.

**Навыки мобов — те же навыки.** Моб ссылается на служебный навык без класса,
как умение предмета, и запускает его по триггеру: появление, промежуток,
получение урона, удар, смерть. Отдельного языка для ИИ нет, и это главное
упрощение против прежнего стека, где у мобов был свой набор механик, пересекающийся
с игровым процентов на восемьдесят.

**Дроп объявлен числами, а не таблицами таблиц.** Строка дропа — предмет или
материал, количество «от и до» и шанс. Вложенные таблицы дропа переносить не
стоило: они дают гибкость, которой почти никто не пользовался, и непредсказуемость,
на которую жаловались все.

**Подмена естественного спавна — правило, а не скрипт.** В файле сказано: в этом
мире вместо такого-то ванильного существа с такой-то вероятностью появляется наш
моб. Этого достаточно, чтобы заселить мир, и это читается целиком, в отличие от
спавнеров с радиусами и условиями, которые приходилось искать по трём файлам.

### M13 · converter — конвертер старых YAML

**Конвертер не притворяется полным.** Он читает объявления мобов MythicMobs и
переносит то, что имеет прямое соответствие: тип, имя, здоровье, урон, броню,
опыт и дроп. Всё остальное — список навыков со своими механиками, условиями и
таргетерами — выписывается в файл отчёта как «не перенесено» с указанием строки.

Так сделано намеренно. Конвертер, который молча пропускает непонятое, оставляет
моба без половины поведения, и обнаруживается это в бою. Конвертер, который
честно говорит «эти двенадцать навыков перенесите руками», экономит ровно те
часы, которые стоило экономить, и не создаёт ложного впечатления, что перенос
закончен.

**Работает через каталоги, а не через чужую папку плагина.** Администратор
кладёт файлы в `convert-in/`, забирает из `convert-out/`. Плагин не читает
каталоги MythicMobs: зависеть от расположения чужого плагина значит сломаться от
его обновления.

**Этап 5 — M14 client-mod.** Только презентация: интерфейс статов, индикаторы
статусов. Версионированный канал. Плагин обязан быть полностью работоспособен
без мода.

### M14 · client-mod — клиентский мод

**Клиент просит, сервер решает.** Версия 2 канала добавила действия от мода:
применить слот, изучить навык, вложить очко, занять слот, выбрать класс. Ни одно
не выполняется «потому что клиент так сказал» — каждое идёт через те же службы,
что и команда в чате, со всеми их проверками и отказами. Подменённый клиент может
попросить ровно то, что игрок может набрать руками, и получит тот же ответ теми
же словами.

**Мод обязателен: без него на сервер не пускают.** Решение владельца проекта,
и цена его записана тут же — любая поломка канала становится поломкой входа.
Поэтому проверка выключается в `config.yml` (`require-mod: false`) без пересборки,
ждёт рукопожатия с отсрочкой (на слабом соединении оно идёт секунды) и никогда не
выгоняет администратора: чинить канал нужно изнутри.

**Статусы контроля стали настоящими.** До этого стан и корни были записью в
реестре: запрещали касты, показывались в интерфейсе, но цель продолжала ходить —
объявление, за которым ничего не стоит. Теперь статус с меткой `immobilize`
обездвиживает: мобу выключается ИИ, игроку обнуляется скорость ходьбы и ставится
предельное замедление с запретом прыжка. Для игрока это не абсолютная
неподвижность — сервер не нажимает за него клавиши, — и так честнее сказать, чем
изображать, будто контроль над игроком и над мобом устроен одинаково.

**Весь урон идёт через один конвейер, включая ванильный.** Раньше конвейер
считал только урон навыков: удар мечом, стрела, падение и огонь проходили мимо, а
вместе с ними мимо проходили физический урон, защита, сопротивление, крит, щиты и
проклятия, снимающие цели процент урона. Все эти числа существовали и ничего не
делали. Теперь обычный урон пересчитывается тем же `DamageEngine` в том же
порядке; свой урон помечается на время применения, иначе он считался бы дважды —
и искали бы это в балансе.

Стрела считается ударом стрелка, стихии и падение — чистым уроном: выдумывать
для огня магическую школу значило бы, что он считается заклинанием.

**Усиление и удлинение эффектов перестали быть мёртвыми статами.**
`effect_power` множит лечение и величины статусов, `effect_duration` — их
длительность. Оба были объявлены в `stats.yml` и не читались никем: число,
которое игрок видит в меню и которое ничего не меняет, — худший вид объявления
без исполнения.

**Отмена урона работает мимо нашего конвейера.** Конвейер считает только урон от
навыков; удар мечом, падение и огонь шли мимо, и кора друида не отменяла ровно
то, ради чего она есть. Теперь категория `immunity` отменяет любой урон целиком,
а метка `absorb-hit` гасит один удар за стак. Слушатель стоит позже триггеров:
пассивка «когда по мне попали» должна успеть ответить до отмены, иначе кора
гасила бы и урон, и собственный ответ.

**Серверная раскладка убрана по решению владельца проекта.** Перехват Shift с
цифрой удалён целиком: он конфликтовал с хотбаром и мешал в бою. Последствие
названо прямо, потому что оно меняет условие этапа: без мода навыки применяются
только командой `/rpg slot <номер>`. Мод перестал быть удобством и стал
практически обязательным для игры — это сознательный размен, а не упущение.

Что без мода осталось полностью: классы, изучение, слоты, предметы, крафт, мобы
и весь интерфейс на сундуках. Не осталось — удобного применения навыков.

**Клавиши назначает игрок, и интерфейс показывает именно их.** Подпись в окне и
на экране берётся из настроек управления, а не придумывается модом: подсказка,
не совпадающая с настройкой, врёт, и после неё перестают доверять всем
остальным. Пока клавиши не назначены, так и написано — «не назначено», одной
строкой, а не шесть раз подряд.

**Навыки — сетка значков, а не список названий.** Шесть названий в столбик
читаются дольше, чем шесть узнаваемых значков, а в бою вспоминают именно значок.
Значки — картинки 32×32 в ромбе, внутри самого jar мода
(`assets/rpgcore/textures/gui/skills/<навык>.png`): ресурспак для них не нужен,
игра грузит ресурсы мода сама. Цвет — по классу, чтобы класс узнавался раньше
рисунка. Любую картинку можно заменить нарисованной руками, положив файл с тем же
именем. Навык без своей картинки рисуется прежним пиксель-артом из кода, а без
него — ромбом цвета класса: новый навык в контенте не должен требовать правки
мода, чтобы его можно было изучить.

Приглушённый значок значит «не изучен»: цвет появляется ровно тогда, когда навык
начинает работать. Слот ставится там же, правой кнопкой, — ходить за этим на
другую вкладку незачем.

**Подсказка показывает посчитанное сервером.** Название, ступень, стоимость,
перезарядка, наибольший урон за попадание — всё приходит с сервера, из той же
таблицы баланса, которой считает бой. Описание лежит в файле навыка и **не
содержит чисел**: переписанное в текст число разъезжается с балансом в первый же
вечер правок, и это проверяет приёмочный тест.

**Экран принадлежит игроку.** Раскладка интерфейса двигается мышью и хранится
долями экрана, а не пикселями: иначе собранная в окне она разъезжается в полном
экране. Любое место, выбранное за игрока, рано или поздно окажется под чужим
интерфейсом — чат слева внизу, карта справа вверху, чужие моды где угодно.

**Ванильные сердца и броня скрыты, здоровье рисует мод.** Две шкалы здоровья на
одном экране — это две правды, а смотрит игрок всё равно на одну. Голод и опыт
остаются ванильными: мод их не заменяет, и убирать чужую шкалу, ничего не давая
взамен, нечестно.

**Класс мод узнаёт сам.** Он приходит в тех же данных, что рисует ХУД.
Если класса нет, окно выбора открывается само — один раз за вход и только на
чистом экране: окно, выскакивающее посреди боя, это не забота, а помеха.

**Клавиши — ванильные настройки управления.** Шесть клавиш слотов и клавиша окна
живут в обычном списке управления, в своей категории. По умолчанию клавиши слотов
**не назначены**: любая цифра занята хотбаром, любая буква — чьим-нибудь модом, а
мод, который молча перехватывает чужую клавишу, выясняется в бою. До назначения
работает серверная раскладка, та же, что у игроков без мода.

**Счётчики ядра — отдельная вещь, не статусы.** Стаки Роста и Увядания у друида,
души у колдуна, печать у мага — это не эффект, который пройдёт, а ресурс, по
которому игрок принимает решения. Поэтому они приходят отдельным списком и
рисуются делениями рядом с полосой ресурса, а не теряются в столбце из восьми
строк. Статус попадает в этот список по метке `counter` в своём файле — решает
контент, а не код мода.

**Имя и цвет статуса — в контенте.** `display` и `color` в `statuses.yml`: иначе
новый статус нельзя покрасить, не пересобрав мод и не раздав его заново всем
игрокам.

**Бафы и дебафы — два ряда значков, а не список строк.** В бою на них смотрят
боковым зрением, и узнаётся рисунок, а не слово. Рядов два, потому что вопросов
два — «что мне помогает» и «что мне мешает»: щит и неуязвимость идут к бафам,
контроль и метки — к дебафам, контроль ещё и в красной рамке. Каждый ряд игрок
ставит сам; место прежнего общего списка достаётся бафам.

На значке — затемнение по прошедшей доле срока и мигание в последние три
секунды; под значком — всё, что статус делает со статами, по строке на стат: значок стата и
вклад в **процентах эффекта** («+12%» скорости, «-8%» защиты), зелёным или
красным. Вклад считает сервер как разницу итога с надбавкой и без неё той же
кривой рейтинга, что и бой, — «+40 к скорости» игроку не говорит ничего, а мод
кривую не знает и знать не должен. Знак — направление стата: у защиты
перевёрнута фраза, но под её значком «+8%» читалось бы как рост. У статуса без
чисел под значком описание. Значки статусов — тоже картинки 32×32 в ромбе
(`textures/gui/statuses/<статус>.png`), той же формы, что значки навыков; статус
без своей картинки рисуется пиксель-артом из кода или ромбом цвета категории с
первой буквой, и новый статус не требует пересборки мода.

**Версия в первом байте каждого сообщения**, не в рукопожатии и не в настройках.
Иначе клиент старой версии читает новый формат и показывает мусор: числа не те,
полоса не та, а жалоба приходит как «плагин врёт». С версией в байте обе стороны
отказываются словами: сервер говорит, кого обновлять, мод повторяет это в чат —
на случай, если он сам ещё не умеет показать такой ответ.

**Клиент ничего не пересчитывает.** Полоса — это `resource / resourceMax` с
сервера, выносливость — `stamina / staminaMax`, перезарядка и заряды рывка —
`remaining / total` с сервера. Любая арифметика на
клиенте означала бы второй источник правды, а расхождение между полосой маны и
настоящей маной игрок заметит раньше нас.

**Состояние уходит только тем, кто поздоровался, и только когда изменилось.**
Первое — чтобы сотня игроков без мода не стоила трафика, который потом ищут как
«сервер подлагывает». Второе избавляет от выбора частоты: сравнение со прошлым
снимком само даёт нужную.

**Копия протокола в моде — сознательное дублирование.** Общий модуль заставил бы
мод зависеть от сборки плагина, а плагин — тащить сборку мода с выкачиванием
NeoForge из сети, из-за чего плагин перестал бы собираться офлайн. Цена решения
одна: копия может отстать. Её платит тест `ProtocolCopyTest` — он падает в тот
момент, когда копию забыли обновить, а не через неделю на сервере.

**Мод не входит в корневую сборку.** `settings.gradle.kts` его не включает:
`./gradlew build` остаётся офлайновым и зелёным. Мод собирается отдельно, из
своего каталога, и для первой сборки нужна сеть.

---

## 7. Стиль кода

Java 21. `record` для данных, `sealed interface` для узлов DSL, `enum` для
закрытых множеств. Без Lombok и без генерации кода: читаемость стека важнее
экономии строк.

Статического изменяемого состояния нет. Реестры создаются в точке входа и
передаются конструктором. Синглтонов нет.

Комментарии объясняют **почему**, а не что. Там, где поведение движка
неочевидно, в комментарии указывается, чем это подтверждено — класс и метод, по
которым проверено. Этот приём перенесён из YAML-конфигов и уже доказал пользу:
без него находки теряются и ошибка повторяется через месяц.

Имена механик и примитивов обязаны означать то, что те делают. `freeze`, который
не обездвиживает, — брак.

## 8. Стратегия тестирования

Пирамида простая, потому что проверять в игре дорого.

**Юнит-тесты (JUnit 5, уже подключён):** M1, M2, M3, M5 целиком. Это чистая
логика, если `platform/` отделён правильно. Для M3 — матрица по отношениям.

**Тест направления зависимостей:** сканирует импорты и падает, если пакет
импортирует то, что ему по карте не положено, или если Bukkit утёк за пределы
`platform/`.

**Интеграционно:** отмена урона региональным плагином, round-trip данных.

**Вживую проверяет владелец.** Это не формальность: баланс, ощущение и всё
визуальное я проверить не могу в принципе. Поэтому ни одна задача не считается
закрытой по факту «собралось» — только по факту вашего прогона в игре.

## 9. Границы

**Всегда:**
- `./gradlew test` перед словами «работает»
- сервер остаётся играбельным на каждом этапе
- один конвейер урона, один реестр статусов
- любой отказ объясним командой, а не чтением кода

**Спросить сначала:**
- отключение или удаление любого существующего плагина
- правка файлов живого сервера в `C:\ProjectSt\1.21.1NeoForgeUpdate`
- всё, что требует перезапуска сервера при игроках
- любое обращение к сети помимо уже выкаченного кеша

**Никогда:**
- писать в `plugins/` живого сервера без явной просьбы
- удалять существующий контент
- утверждать, что поведение в игре проверено, если его проверяли не вы
