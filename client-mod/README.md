# RpgCore — клиентский мод

Только презентация и просьбы: полосы, счётчики ядра, кольца перезарядки, окно
героя. Мод **ничего не решает**. Каждое действие от него — изучить навык,
занять слот, выбрать класс, применить навык — идёт через те же службы, что и
команда в чате, со всеми их проверками и отказами. Злонамеренный клиент может
попросить ровно то, что игрок может набрать руками, и получит тот же ответ.

## Мод обязателен

Без рукопожатия игрока не пускают на сервер — это делает `ModGate` на стороне
плагина, и отключается одной строкой `require-mod: false` в `config.yml`.

Но правила всё равно живут только на сервере, и это не формальность: меню
открывается и командой, навык применяется и через `/rpg slot N`, а сервер,
оставшийся без единого игрока с модом, продолжает работать целиком. Мод — способ
показать и попросить, а не способ что-то сделать.

## Встраивание в чужой инвентарь

Если на клиенте стоит мод `rpgui` (своё окно инвентаря с закладками), книга
героя появляется в нём отдельной закладкой. Сделано отражением и **без единой
ссылки на его классы**: интерфейс закладки реализован `java.lang.reflect.Proxy`,
вызовы разбираются по имени метода. Своего способа добавить закладку он не даёт,
а зависимость на его сборку означала бы, что наш мод без неё не собирается и не
запускается.

Поэтому его правка ничего не ломает: в худшем случае закладка не появится, о чём
будет одна строка в журнале, а книга по-прежнему открывается своей клавишей.
Встраивание — удобство, а не единственный путь.

Вид один на всё — и в меню, и в бою: чёрное поле, золотая волосяная черта, много
воздуха. Рамы нет намеренно: рама вокруг тёмного поля спорит с тем, что в поле
нарисовано, а здесь самое яркое и есть содержимое — цветные ромбы навыков и
полосы.

Окна и полосы рисуются заливками, без картинок: так окно одинаково выглядит при
любом масштабе интерфейса. Картинки есть только у значков навыков и статусов —
PNG 32×32 в ромбе в `src/main/resources/assets/rpgcore/textures/gui/{skills,statuses}`.
Они лежат в самом jar мода, ресурспак игроку не нужен. Файл называется по
идентификатору навыка или статуса; заменить значок — значит положить другой PNG
с тем же именем. Без картинки рисуется прежний пиксель-арт из кода.

## Эффекты навыков

Сервер присылает по каналу `rpgcore:fx` «что и где» готовыми числами: радиус
— тот, которым выбирались цели (со статом радиуса), срок зоны — тот, с которым
она поставлена, крит — из конвейера урона. Мод решает только «как красиво».
**Граница области всегда рисуется ровно по присланному радиусу** тонкой яркой
чертой посередине полосы; заливка, руны и искры вокруг — украшение, по
которому радиус не определяют.

Своих записей в реестрах у мода нет — ни `ParticleType`, ни чего-либо ещё:
реестр типов частиц синхронизируется с сервером, и запись, которой нет на
сервере, после входа осталась бы без числового номера. Всё рисуется геометрией
в `RenderLevelStageEvent` (стадия после частиц) с аддитивным смешиванием.
Подробности и ссылки на исходники NeoForge — в шапке `FxDraw` и в `SPEC.md`.

Текстуры эффектов лежат в jar (`textures/fx`), белые с прозрачностью — цвет
даёт эффект. Их рисует `tools/fx/generate.py`; любую можно заменить PNG с тем
же именем.

Игрок без мода видит ванильные частицы из тех же навыков, игрок с модом —
**только эффекты мода, ни одной ванильной частицы навыков**. Дублей нет: сервер
шлёт каждому один вид. Действие без своего `fx` у игрока с модом тоже не
ванильное — мод рисует общий эффект его формы в облике класса.

У каждого класса свой облик (`FxStyle.Look`): основной цвет, блик и форма искр —
звёзды мага, угли берсерка и воина, листья друида, дымка колдуна и убийцы,
осколки плута, звёзды ловкача, наконечники охотника, молнии ударника. Формы
искр — текстуры `ember`, `leaf`, `wisp`, `shard`, `star`, `chevron`, `zap` рядом
с остальными.

### Как добавить эффект новому навыку

1. В файле навыка рядом с ванильной частицей поставить `fx`:

   ```yaml
   - { action: particles, particle: flame, shape: ring, count: 40, size: radius, fx: warrior_spin_wave }
   - { action: zone, tag: totem, radius: $radius, duration: $duration, particle: end_rod, fx: shaman_totem }
   - { action: projectile, range: $range, particle: crit, fx: hunter_arrow, on-hit: hunter_arrow_hit }
   - { action: teleport, forward: $distance, particle: portal, fx: rogue_blink_trail }
   ```

   `particle` обязателен — это вид для игроков без мода. Для границы области
   размер пишется `size: radius`: тогда он равен радиусу выборки шага, и шаг
   должен сам выбирать цели радиусом.

   Проще всего взять роль класса: `<класс>_wave` (граница области), `_aura`
   (круг вокруг себя), `_rise` (бафф, лечение), `_sink` (метка, проклятие на
   цели), `_flash`, `_blast`, `_puff` (удар, взрыв, всплеск), `_bolt` (снаряд),
   `_zone` (зона). Цвет и искры придут из облика класса.

   Украшение рядом со своим эффектом в том же шаге — `fx: none`: мод его не
   рисует, игроку без мода остаётся ванильная частица.

2. Если роли класса мало — добавить в `FxStyle` свою строку каталога: вид
   (`ZONE`, `WAVE`, `CONE`, `IMPLODE`, `TELEGRAPH`, `FLASH`, `BOLT`, `TRAIL`,
   `RISE`, `SINK`), цвета, сроки в тиках, руны и густоту искр. Цвет `0` — цвет
   класса, форма искр — мотив класса, если не задана своя.

3. Собрать мод. Тест плагина `ShippedContentTest` проверяет, что у каждого
   видимого действия поставляемого контента есть `fx` и что каждый `fx` есть
   в каталоге мода.

Незнакомый `fx` рисуется общим эффектом своей формы в облике класса — граница
при этом всё так же точная, — но в поставляемом контенте его не пропустит тест.

## Сборка

Мод **не входит** в корневую сборку `rpgcore`: для него нужна сеть, чтобы
выкачать NeoForge и его зависимости, а плагин собирается офлайн. Поэтому
корневой `settings.gradle.kts` его не включает, у мода своё `settings.gradle`, и
`./gradlew build` в корне его не трогает.

Собирать из корня проекта:

```
./gradlew -p client-mod build
```

Первая сборка требует сети и занимает около двух минут: NeoForge выкачивается и
кладётся в кеш. Нужен JDK 21.

Готовый файл — `client-mod/build/libs/rpgcore-client-1.0.0.jar`.

## Куда ставить

В папку `mods` **клиента** игрока. Не в `Mods` сервера: мод клиентский
(`dist = Dist.CLIENT`), серверу он не нужен и ничего там не делает.

Проверка на сервере — `/rpg client`: там видно, кто поздоровался, с какой
версией мода и какая версия протокола у плагина.

## Протокол

Файлы `src/main/java/ru/projectst/rpgcore/net/` — **копия** классов из плагина.
Это сознательное дублирование: общий модуль заставил бы мод зависеть от сборки
плагина, а плагин — тащить сборку мода. Копия защищена тем, что формат проверен
тестами в плагине и несёт версию в первом байте каждого сообщения: при
расхождении версий сервер отказывает словами, а не присылает мусор.

При изменении формата: поправить `Protocol.VERSION` в плагине, скопировать
файлы протокола сюда (`Protocol`, `ClientState`, `StateCodec`, `MenuData`,
`FxMessage`), собрать мод заново. Расхождение ловит `ProtocolCopyTest`.
